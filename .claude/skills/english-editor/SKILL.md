# English editor (MIT Sloan / IMD)

Скіл редагує англійський текст сайту так, щоб він звучав як сильний B2B-видавець для керівників, а не як переклад чи AI-текст. Він править файли одразу і пам'ятає, що вже відредаговано.

## Файли скіла

| Файл | Що в ньому | Коли читати |
|---|---|---|
| `references/style-guide.md` | Читач, регістр MIT/IMD, правила, заборонені штампи, «що не чіпати», приклади до/після | Перед першою правкою, завжди |
| `references/humanizer-rules.md` | Паттерни AI-тексту (копія з 8move `humanizer.ts`) | Перед другим проходом |
| `scripts/units.mjs` | Ділить текст на юніти, рахує хеші, порівнює з `state.json` | На початку і після кожного юніта |
| `state.json` | Хеші відредагованих юнітів | Не редагуй руками |
| `pending-translations.md` | Накопичений список ключів en, які змінились і чекають на переклад de/fr/it | Дописуй після кожного юніта |

**Юніт** — це одиниця роботи: секція `messages/en.json` (великі секції діляться на ключі другого рівня, напр. `messages:pages.home`) або один файл у `src/data/` (напр. `data:src/data/case-studies/clinic-voice-documentation.ts`). Секція `legal` і файли перекладів (`de.ts`, `fr.ts`, `it.ts`) у юніти не входять.

## Аргумент

- Без аргументу — усі pending-юніти сайту.
- З аргументом — фільтр за підрядком id: `/english-editor pages.home`, `/english-editor case-studies`.

## Процес

```
pending ──> для кожного юніта:
             1. прочитати
             2. прохід MIT/IMD (правка файлу)
             3. прохід humanizer
             4. перевірка інваріантів
             5. mark + pending-translations
         ──> pnpm test ──> підсумок
```

0. Запусти з кореня репо: `git status --short`. Якщо в файлах, які зачепить скіл, є незакомічені чужі зміни — зупинись і спитай користувача. Паралельна сесія може їх втратити.
1. `node .claude/skills/english-editor/scripts/units.mjs pending [фільтр]` — список юнітів. Якщо список порожній, скажи це і завершуй.
2. Прочитай `references/style-guide.md` і `references/humanizer-rules.md`.
3. Для кожного юніта по черзі:
   1. Прочитай текст юніта. У `src/data/` редагуй тільки англійські рядки: поля верхнього рівня і блоки `en: {…}`. Блоки `de`, `fr`, `it` і `translations` не чіпай.
   2. **Прохід MIT/IMD.** Перепиши рядки за style-guide: читач — керівник, результат бізнесу перед технологією, активний стан, британський правопис, sentence case, без штампів. Рядок, який уже добрий, залиш як є. Не правка заради правки.
   3. **Прохід humanizer.** Перевір відредаговані рядки проти `humanizer-rules.md` і спитай себе: «Що досі звучить як AI?» Виправ.
   4. **Інваріанти.** Ключі, плейсхолдери `{…}`, теги `<…>`, markdown-структура, URL, slug, числа, імена — ті самі, що до правки. Рядок не довший за оригінал. UI-лейбли — ±20 % довжини. Для `messages/en.json` перевір, що JSON валідний: `node -e "JSON.parse(require('fs').readFileSync('messages/en.json','utf8'))"`.
   5. `node .claude/skills/english-editor/scripts/units.mjs mark <id>` — навіть якщо змін не було. Так наступний запуск не перевірятиме юніт знову.
   6. Допиши в `pending-translations.md` змінені ключі (формат нижче). Якщо змін не було — нічого не дописуй.
4. Після всіх юнітів запусти тести: `source ~/.nvm/nvm.sh && nvm use 20` (engines: `^18.20.2 || >=20.9.0`), потім `pnpm test`. Якщо тест упав через твою правку — поверни число або факт і перезапусти. Якщо тест падав і до правок — скажи про це, не виправляй чужий тест.
5. Не комітай. Коміт — тільки на запит користувача.

## Формат pending-translations.md

Файл накопичується між запусками. Користувач або скіл перекладу видаляє рядки, коли переклад оновлено.

```markdown
## 2026-11-18
- messages/en.json → home.hero.subtitle
- messages/en.json → home.cta.title
- src/data/case-studies/clinic-voice-documentation.ts → content.en.hero.tagline
```

## Підсумок для користувача

Відповідь українською, коротко:

1. Скільки юнітів оброблено, скільки змінено, скільки лишилось (`units.mjs status`).
2. Таблиця 5–10 найпоказовіших правок: файл/ключ, до, після, чому (одне речення — правило зі style-guide). Мета — щоб людина вчилась, а не лише копіювала.
3. Що варто перевірити людині: місця, де ти сумнівався щодо змісту або де текст обіцяв щось, чого ти не міг перевірити.
4. Результат `pnpm test`.
5. Нагадування: `pending-translations.md` має N ключів для de/fr/it.

## Чому так

- **Стейт за хешем**, а не за датою: якщо хтось змінить англійський текст пізніше, хеш зміниться, і юніт знову стане pending. Невідредаговане старе не губиться, відредаговане не правиться двічі.
- **Хеш data-файлу — весь файл.** Зміна перекладу в тому ж файлі теж зробить юніт pending. Це дешевше, ніж парсити TypeScript, і такий юніт швидко проходить без змін.
- **Факти не чіпаємо.** Сайт продає довіру. Вигадана цифра чи гучніша обіцянка шкодить більше, ніж незграбне речення.
